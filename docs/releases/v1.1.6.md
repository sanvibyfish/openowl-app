# openOwl v1.1.6 Release Notes

> **Status**: ✅ Done | **Notes Ready**: 2026-08-21 | **Released**: 2026-08-24 (tag `v1.1.6`)

Git subprocess reliability and editor data safety, plus the Right Dock state isolation and Terminal AppleScript automation originally planned as v1.1.5 (v1.1.5 was never tagged; its contents ship here). This release rewrites the git subprocess pipe layer — read errors are no longer swallowed, waits are bounded, and timeouts no longer use SIGKILL — corrects the "Discard All" contract, which did not do what its label promised, fixes a path that could lose editor content on ⌘Q, and removes three fallbacks that were masking real errors.

---

## Bug Fixes

### Git subprocess pipes no longer return truncated data

- `GitPipeDrain`'s `DispatchIO` read handler discarded its `error` argument: hitting EIO/ECANCELED mid-read still signalled completion as usual, `finish()` returned a **truncated** buffer, and callers checked only the exit code — so half a `git status` / `git diff` was treated as a complete result. This surfaced as the Git panel listing fewer files than it should, users staging or discarding based on an incomplete diff, and no log entry anywhere. Read errors are now logged and make `finish()` throw.
- `finish()` waited without a timeout. A pipe that does not reach EOF after the child exits means a grandchild (a hook, a credential helper, an fsmonitor daemon) inherited the write end and is still alive — the caller then blocked forever, and for `status()` that also deadlocked **every subsequent status** on that repository's gate lane. The UI showed a spinner that never resolved, or a panel that simply stopped refreshing, with no error. The wait is now bounded by a 5-second grace period and throws a specific error on timeout.
- Command timeouts now terminate with `SIGTERM` instead of `SIGKILL`. SIGKILLing a git that is refreshing the index leaves a stale `.git/index.lock` behind, which jams every later git command in that repository.
- `fileData` (`git show`) built its own Process and two Pipes and called `readDataToEndOfFile()` on them in sequence. The comment claimed it "reads both pipes first to avoid deadlock", but that call blocks — so filling the stderr buffer while stdout is being read deadlocks exactly as before. It now goes through `launchGit`.
- `hasUncommittedChanges` ran a bare `git status --porcelain` directly, bypassing the per-repo gate, the signal retry and the timeout — none of the three protections added in the 2026-08-11 SIGBUS hardening. It now goes through `status()`.
- `CommitMessageGenerator` had the same defect: its `terminationHandler` called `readDataToEndOfFile()` only after the process exited, so a claude CLI that filled 64KB of stdout never exited, the handler never fired, and the generate button spun forever. It now reuses `GitPipeDrain`.

### "Discard All" now really discards everything

- It ran `git checkout-index --all --force`, which restores the working tree **from the index**, not from HEAD. Since `commit()` stages automatically, a dirty index is the normal state — so after pressing a button labelled "Discard all tracked and untracked changes", staged modifications survived untouched, staged deletions stayed deleted, and the next commit carried content the user believed they had thrown away.
- It now runs `git reset --hard HEAD` + `git clean -f -f -d` (`git rm -r --cached` for an empty repository). The confirmation dialog states the actual scope: staged, unstaged and untracked changes are all discarded, and untracked nested Git repositories are removed.

### The editor no longer loses content on ⌘Q

- When a save was rejected because the file had changed on disk, the code advanced that tab's disk signature so a second ⌘S would overwrite. But the bulk save behind ⌘Q and project switching tries each tab exactly once: the signature advanced, the save failed, nobody handled it, and the edits were gone. It also left the tab looking synced with disk, so `reloadOpenTabFromDiskIfNeeded` skipped it from then on — the editor showed stale content while claiming to be current.
- Overwrite confirmation is now tracked as separate state that only an explicit single-tab ⌘S consumes. Bulk saves neither overwrite on the user's behalf nor advance the signature.

### Terminal surface creation failures are recoverable

- After a failed surface creation, the view retries when it is reattached to a window. Creation needs a real window — it reads `backingScaleFactor` to build the Metal layer — and the conditions that break it are usually transient: the ghostty app still initialising, the Metal device momentarily unavailable, memory pressure. Previously a single failure locked that pane permanently.
- The retry runs only when the window changes, never per layout, so a persistent failure cannot spin. The old notice is removed before retrying, so notices never stack.
- AppleScript input to a failed pane still returns a terminal error rather than `notReady`: a script cannot cause a reattach itself, so reporting `notReady` would send it into a retry loop its own retries can never resolve.

### Miscellaneous

- AppleScript `input text` silently dropped the text and reported success when the target pane's surface did not exist yet. The surface is created in `viewDidMoveToWindow`, and `input text` immediately after `make new tab` is the standard way to write such a script. It now returns a `notReady` error.
- The File Explorer rename commit guard relied on `NSControl.currentEditor()`, whose value at `controlTextDidEndEditing` time carries no AppKit ordering guarantee. It now tests whether the cell is still in the view hierarchy, which distinguishes the user clicking elsewhere from `reloadData` pulling the field editor away.
- `CommitMessageGenerator.cancel()` could call `terminate()` on a `Process` that was never started, raising an `NSInvalidArgumentException` that Swift cannot catch, crashing the app. The process is now registered only after it starts successfully.
- The sidebar header button sits against the trailing edge again. `plus.diamond` had drifted to the middle of the header because several branches shared one trailing `Spacer`, which split the free width with the `Spacer` already inside the branch. Each branch now holds its own.

## Removals

### Three fallbacks removed — a missing dependency should raise an error, not be papered over

- **The git launch-failure retry.** The root cause of EBADF was `GitPipeDrain` leaking the duplicated read-end fd: libdispatch does not close the fd of an fd-based channel for you, so every git launch leaked 2, exhausting the fd table after roughly 37 hours of continuous use. That is now fixed by an explicit `close(descriptor)` in the cleanup handler. The retry layer was a stopgap from before the root cause was known, and it shared an attempt budget with the signal retry — weakening SIGBUS recovery rather than helping it.
- **`GitExecutable`'s PATH fallback.** `return "git"` never worked: `Process` resolves a relative path against the process cwd, not PATH. All it did was turn "there is no git on this machine" into a vague launch failure that got classified as transient and retried repeatedly. If none of the three candidate paths is executable, it is now a `preconditionFailure`.
- **The defensive fallback after the retry loop.** Its comment called it unreachable; it was reachable — exhausting the signal-retry and launch-retry budget lands there — and it fabricated an error with `exitCode: 0` and empty stderr, disguising a launch failure as a verdict from git. The UI showed `` `git …` failed (0): Unknown git error``.
- Git calls that succeed with non-empty stderr are now written to the `[git]` log. Git often expresses partial failure as exit 0 plus a stderr warning — an unreadable directory leaving files unstaged, for instance.

### `AppExitMonitor` and `exit.log` removed

A single-purpose diagnostic added to track down the exit(1) of 2026-08-11. It answered no user requirement, yet permanently rewrote the process's SIGTERM/SIGABRT semantics, and was unreliable on its own terms: it used `signal()` rather than `sigaction()` and did not save the previous handler, so the libghostty (Zig) panic handler installed afterwards overwrote it; without `SA_ONSTACK`/`sigaltstack` a stack-overflow SIGSEGV could never reach the handler at all; and a partially failed installation only wrote an NSLog while `install()` returned `Void`. See [FEAT-009](../features/009-app-logger.md).

### Cross-agent message bus removed

Removed per [REQ-009](../requirements/REQ-009-message-bus.md).

## Retracted content

An earlier version of this file listed a message-bus naming entry point for split panes (`PaneDragHandle` right-click → Set Message Bus Name…) as the headline feature of v1.1.6. That feature **was never implemented**: `git log -S "Set Message Bus Name"` matches exactly two commits, one introducing the string and one deleting it, and the only terminal UI file the introducing commit touched was `FreeTerminalTabBar.swift` — never `TerminalWorkspaceView.swift`, where `PaneDragHandle` is defined. The only entry point that ever existed was the Free Terminal tab pill, itself deleted with [REQ-009](../requirements/REQ-009-message-bus.md) on 2026-08-18. The `buslib.py` timezone fix entry is retracted along with it: that file was deleted with REQ-009 too.
