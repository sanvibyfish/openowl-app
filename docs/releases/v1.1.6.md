# openOwl v1.1.6 Release Notes

> **Status**: 🟢 Ready | **Notes Ready**: 2026-08-21 | **Released**: 尚未发布（无 tag）

Git 子进程可靠性与编辑器数据安全版本。本版本重写了 git 子进程的管道层（读错误不再被吞、等待有界、超时不再用 SIGKILL），修正了 "Discard All" 名不副实的契约，修复了 ⌘Q 时可能丢失编辑内容的路径，并移除了三处会掩盖真实错误的兜底。

---

## Bug Fixes

### Git 子进程管道不再返回截断数据

- `GitPipeDrain` 的 `DispatchIO` 读回调此前丢弃 `error` 参数：读到一半遇到 EIO/ECANCELED 仍照常发出完成信号，`finish()` 返回**已截断**的缓冲区，而上游只检查退出码，于是半截 `git status` / `git diff` 被当成完整结果。表现为 Git 面板少列文件、用户基于不完整 diff 执行 stage/discard，且全程无日志。现在读错误会被记录并使 `finish()` 抛出。
- `finish()` 此前无超时等待。子进程退出后管道仍不 EOF，意味着孙进程（hook、credential helper、fsmonitor daemon）继承了写端且仍存活——此时调用方会永久阻塞；对 `status()` 而言还会连带锁死该仓库 gate lane 的**全部后续 status**，UI 表现为「一直转」或「再也不刷新」且无错误。现在以 5 秒宽限期有界等待，超时抛出明确错误。
- 命令超时的终止信号由 `SIGKILL` 改为 `SIGTERM`：SIGKILL 掉正在刷新 index 的 git 会留下 stale `.git/index.lock`，卡死该仓库后续所有 git 命令。
- `fileData`（`git show`）此前自建 Process 与两个 Pipe 并顺序 `readDataToEndOfFile()`——注释声称「先读两个管道以避免死锁」，而该调用是阻塞的，读 stdout 期间 stderr 缓冲区填满即死锁。现已收编进 `launchGit`。
- `hasUncommittedChanges` 此前直接跑裸 `git status --porcelain`，绕过了 per-repo gate、信号重试与超时——即 2026-08-11 SIGBUS 加固的三项保护一项都没有。现改走 `status()`。
- `CommitMessageGenerator` 存在同类缺陷：`terminationHandler` 在进程退出后才 `readDataToEndOfFile()`，claude CLI 写满 64KB stdout 即永不退出、handler 永不触发、生成按钮永久转圈。现复用 `GitPipeDrain`。

### "Discard All" 现在真的丢弃全部改动

- 此前执行 `git checkout-index --all --force`，即**从 index 恢复工作区**而非从 HEAD。由于 `commit()` 会自动 stage，index 脏是常态——用户点下写着「Discard all tracked and untracked changes」的按钮后，已暂存的修改原封不动保留，已暂存的删除仍是删除状态，随后的提交会带上他以为已丢弃的内容。
- 现改为 `git reset --hard HEAD` + `git clean -f -f -d`（空仓库走 `git rm -r --cached`）。确认对话框同步写明：staged / unstaged / untracked 全部丢弃，且会删除未跟踪的嵌套 Git 仓库。

### 编辑器不再在 ⌘Q 时丢失编辑内容

- 保存因「文件已在磁盘上变更」被拒绝时，代码会推进该 tab 的 disk signature，用意是让用户再按一次 ⌘S 即可覆盖。但 ⌘Q / 切换项目走的批量保存对每个 tab 只尝试一次：signature 被推进、保存失败、无人处理，编辑内容随即丢失。该行为还会使 tab 被误判为「已与磁盘同步」，`reloadOpenTabFromDiskIfNeeded` 从此永远跳过它，编辑器显示陈旧内容却声称是最新的。
- 覆盖确认现由独立状态跟踪，只有显式的单 tab ⌘S 能消费；批量保存不会代替用户覆盖，也不再推进 signature。

### 其它

- AppleScript `input text` 此前在目标 pane 的 surface 尚未创建时静默丢弃文本并返回成功（surface 在 `viewDidMoveToWindow` 才创建，而 `make new tab` 后立即 `input text` 是标准脚本写法）。现返回 `notReady` 错误。
- 文件浏览器重命名的提交守卫此前依赖 `NSControl.currentEditor()`，而该值在 `controlTextDidEndEditing` 触发时是否已置空并无 AppKit 时序保证。现改用「cell 是否仍在视图层级中」判定，可区分用户点击别处与 `reloadData` 拉走 field editor。
- `CommitMessageGenerator.cancel()` 此前可能对尚未启动的 `Process` 调用 `terminate()`，抛出 Swift 无法捕获的 `NSInvalidArgumentException` 导致崩溃。进程现仅在成功启动后注册。

## Removals

### 移除三处兜底（缺依赖应当报错，而非被掩盖）

- **git 启动失败重试**：EBADF 的根因是 `GitPipeDrain` 泄漏 dup 读端 fd（libdispatch 对 fd-based 通道不自动关闭 fd，每次 git 启动 +2 fd，连续运行约 37 小时后 fd 表耗尽），该根因已由 cleanup handler 显式 `close(descriptor)` 修复。重试层是修根因之前的权宜措施，且与信号重试共用同一 attempt 预算，反而削弱了 SIGBUS 重试。
- **`GitExecutable` 的 PATH 回落**：`return "git"` 从不生效——`Process` 对相对路径按进程 cwd 解析而非查 PATH。它把「机器上没有 git」变成一个会被归类为「瞬时错误」并反复重试的模糊启动失败。现改为三个候选路径都不可执行即 `preconditionFailure`。
- **循环后的 defensive fallback**：注释自称不可达，实为可达（信号重试 + 启动重试耗尽预算即落入），且会构造 `exitCode: 0` + 空 stderr 的错误，把启动失败伪装成 git 的判决，UI 显示 `` `git …` failed (0): Unknown git error``。
- 成功但 stderr 非空的 git 调用现写入 `[git]` 日志。git 常以「exit 0 + stderr 警告」表达部分失败（如目录不可读导致文件未被 stage）。

### 移除 `AppExitMonitor` 与 `exit.log`

为定位 2026-08-11 的 exit(1) 而加的一次性诊断设施，不对应任何用户需求，却常驻改写了进程的 SIGTERM/SIGABRT 语义，且自身不可靠：用 `signal()` 而非 `sigaction()`，不保存原 handler，会被随后安装的 libghostty(Zig) panic handler 覆盖；无 `SA_ONSTACK`/`sigaltstack`，栈溢出型 SIGSEGV 根本进不了 handler；安装部分失败仅写 NSLog 而 `install()` 返回 `Void`。详见 [FEAT-009](../features/009-app-logger.md)。
