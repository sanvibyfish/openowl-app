# openOwl v1.1.4-2 Release Notes

**Release Date**: 2026-08-09

AppKit drag-and-drop stability patch. v1.1.4-2 removes the SwiftUI drop target above terminal panes and routes pane rearrangement through the existing AppKit terminal hierarchy. This fixes nested splits that accepted pane drops only in part of the layout, prevents drag handling from blocking terminal input, and stops hidden panes from intercepting Finder file drops.

---

## Bug Fixes

### Pane dragging now reaches every nested split

The pane drop destination previously lived in a SwiftUI overlay created after a drag started. In nested layouts, the destination was not reliably registered before AppKit entered its dragging session, so only some panes accepted the drop.

Each visible `TerminalScrollView` is now a native AppKit dragging destination for the private `com.openowl.terminal.pane-drag` pasteboard type. Drop zones are calculated in the target view's own coordinates:

- Left, right, top and bottom edge zones reposition the source pane beside the target
- The center zone swaps the source and target panes
- Dropping directly on another pane's three-dot handle performs the same center swap through `PaneHandleNSView`

The implementation works with the flat pane layout and does not change the split tree model.

### Drag handling no longer blocks terminal input

The full-pane SwiftUI `.onDrop` / `contentShape` overlay has been removed. It sat above `TerminalNSView` in hit testing and could leave the terminal unable to receive clicks, text selection or keyboard focus after view state changed.

SwiftUI now only lays out pane frames, handles visibility and renders search UI. Drag source, drag destination, drop-zone updates, completion and cancellation stay in AppKit.

### Hidden panes no longer steal Finder or pane drops

Inactive tabs and panes hidden by maximize remain mounted to preserve their terminal surfaces. They previously remained registered as dragging destinations, allowing AppKit to route a file or pane drag to an invisible terminal.

`TerminalScrollView.setTerminalVisibility(_:)` now registers file, URL, text and pane drag types only while the pane is visible, and unregisters them when hidden. The matching three-dot handle follows the same visibility rule.

### Project context synchronization no longer cancels an active drag

Terminal OSC 7 working-directory updates can resynchronize the active project while a pane drag is in progress. Re-entering the same namespace previously cleared `draggingPaneID`, causing every target to reject the rest of that AppKit dragging session.

Drag state is now cancelled only when the namespace actually changes. Cancellation also clears orphaned target and drop-zone state and removes the AppKit highlight.

## Behavior Changes

| | v1.1.4-1 | v1.1.4-2 |
|---|---|---|
| Pane drop destination | SwiftUI full-pane overlay | Native `TerminalScrollView` / `PaneHandleNSView` destinations |
| Nested split dragging | Some panes may not accept a drop | Every visible pane accepts edge and center zones |
| Terminal hit testing during drag state changes | SwiftUI overlay can block the terminal | No full-pane SwiftUI drag target above `TerminalNSView` |
| Finder drop routing | Hidden mounted panes can intercept the drag | Hidden panes unregister dragged types |
| Same-project OSC 7 synchronization during pane drag | Can cancel the active drag | Active drag state is preserved |
| Maximize / restore | AppKit handle double-click or ⇧⌘↩ | Unchanged |

## Validation

374 tests pass across 32 suites. New regression coverage verifies:

- Re-entering the same project namespace preserves active pane drag state
- Cancelling a drag clears orphaned target and drop-zone state
- Repeated cancellation remains idempotent

Runtime verification covered:

- Terminal click, focus and command input after the AppKit migration
- Pane rearrangement across nested splits
- Handle-to-handle center swaps
- ⌘W before and after pane rearrangement; only the focused pane closes and remaining surfaces continue rendering

Finder automation did not initiate a real macOS dragging session, so Finder-to-terminal file insertion remains an explicit manual smoke-test item below.

## Smoke Test Checklist

| # | Scenario | Expected |
|---|----------|----------|
| 1 | Create a 2×2 nested split and drag each pane onto every other pane | Every visible pane shows a drop highlight and accepts the drop |
| 2 | Drop near the left, right, top and bottom edges | Source pane moves to the corresponding side of the target |
| 3 | Drop in the center of a pane | Source and target panes swap |
| 4 | Drop a three-dot handle directly on another handle | Source and target panes swap |
| 5 | Cancel a drag with Esc, outside the window and back on the source | Highlight clears; terminal input remains responsive |
| 6 | Click each terminal and type a command after repeated drags | Every terminal receives focus and input normally |
| 7 | Drag a file from Finder into each visible pane | The file path is inserted into the pane under the pointer |
| 8 | Switch projects, then drag a Finder file into the visible terminal | No hidden project's terminal receives the path |
| 9 | Maximize a pane and drag a Finder file into it | The visible maximized pane receives the path; hidden panes do not |
| 10 | Double-click the maximized pane's handle | Original split and ratios return |
| 11 | Rearrange a pane, then press ⌘W | Only the focused pane closes; remaining terminal surfaces keep rendering |
