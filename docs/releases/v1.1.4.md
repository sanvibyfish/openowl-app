# openOwl v1.1.4 Release Notes

**Release Date**: 2026-08-05

Drag-and-drop fix release. A cancelled pane drag used to leave an invisible drop overlay covering every other pane — swallowing terminal clicks, text selection, Finder file drops, and the drag handle itself — until the app was restarted. The same handle's double-click maximize/restore was broken by the SwiftUI `.onTapGesture` + `.onDrag` conflict. v1.1.4 fixes both by moving the handle to AppKit, and also fixes an unrelated oscillation in the file-tree divider.

---

## Bug Fixes

### A cancelled pane drag froze mouse input until restart

Dragging a pane by its three-dot handle sets `draggingPaneID`, which mounts a `Color.clear.contentShape(Rectangle())` drop overlay on every *other* pane. That state was only cleared in `PaneDropDelegate.performDrop()` — the success path. Pressing Esc, releasing outside a valid target, or dropping back on the source pane never reached it, so the overlay stayed mounted forever.

The consequences compounded, because the overlay is an `.overlay` on the whole `VStack` — and the drag handle is that VStack's first child:

- **Terminal clicks and text selection stopped working** — the `contentShape` swallowed them
- **Finder file drops were rejected** — AppKit hit-tests top-down for a registered drag destination and does not fall through to an occluded sibling when the topmost one declines, so `TerminalScrollView` never saw the drop. The private `paneDragTypeID` did not help: what blocks the drop is the overlay's *existence*, not which types it accepts
- **No blue drop-zone highlight appeared on the next drag** — not a rendering bug; the handle itself was buried under the overlay, so `.onDrag` never fired and no drag session ever started
- **The state could not be cleared by hand** — with the handle unreachable, no further drag could complete and reach `performDrop`

A guard for this had existed since v1.0.9 (`d6f9c1a`): an `NSEvent` local monitor on `.leftMouseUp` calling `cancelDragIfActive()`. **It never fired.** Once AppKit opens an `NSDraggingSession` it runs its own event loop and consumes the mouseUp without routing it through `NSApp.sendEvent`, where local monitors observe. The monitor's own comment assumed mouseUp and `performDrop` arrived in one event dispatch; they are on different paths entirely.

**Fix:** the three-dot handle is now an AppKit `PaneHandleNSView` that owns the drag session (`beginDraggingSession` + `NSDraggingSource`). Its `draggingSession(_:endedAt:)` callback clears state on every end path — success, Esc, outside, back-on-source. The dead `.leftMouseUp` monitor was removed rather than left as a second layer.

### Double-click on the three-dot handle did not maximize or restore

SwiftUI's `.onTapGesture(count: 2)` delays the initial mouseDown while waiting for a second click. Stacked under `.onDrag` on the same handle, that delay corrupted the drag session (drops silently failed) and the double-click itself often never fired. Moving interaction into `PaneHandleNSView` — double-click on `mouseDown` with `clickCount >= 2`, drag on `mouseDragged` — makes both paths reliable. Maximize still does not touch the split tree; restore returns the exact ratios.

### The file-tree divider oscillated instead of tracking the mouse

The divider between the file tree and the editor used a `DragGesture` with the default `.local` coordinate space. The divider sits *between* the two panels, so widening the tree moves the divider itself — and with it the origin the translation is measured against, cancelling the gesture out every frame:

```
mouse +100px → translation 100 → width 240 → 340
next frame, divider now at 340 → same mouse position reads translation 0 → width back to 240
```

**Fix:** `coordinateSpace: .global`, matching the right dock's width handle, which hit this exact problem earlier and carries a comment explaining it. This divider was missed at the time.

## Observability

Pane-drag instrumentation moved from bare `NSLog` to `AppLogger` under the `pane-drag` tag, so it lands in `~/Library/Logs/openOwl/openowl.log` instead of only the system log.

This mattered directly: while diagnosing the bug above, the app's log file contained 761 entries for the day and not one came from a drag. Release builds emit `NSLog` at the os_log default level, which is not persisted — the drag path was effectively unobservable in shipped builds, and the failed `.leftMouseUp` guard had gone unnoticed for nearly five months as a result.

The tag is always on; dragging is a low-frequency interaction with no hot-path cost.

## Behavior Changes

| | v1.1.3 | v1.1.4 |
|---|---|---|
| Cancelling a pane drag (Esc / outside / back on source) | Overlay stays mounted; terminal input, file drops and the handle are dead until restart | State clears on drag-session end; everything keeps working |
| Finder file drop after a cancelled pane drag | Rejected | Accepted |
| Double-click three-dot handle | Often no-op (gesture conflict with drag) | Maximizes / restores that pane |
| Dragging the file-tree divider | Oscillates between the start width and the mouse position | Tracks the mouse |
| Pane-drag diagnostics | System log only, not persisted in release builds | `[pane-drag]` in `~/Library/Logs/openOwl/openowl.log` |

## Tests

372 existing tests pass. No new unit tests: both defects live in SwiftUI gesture and AppKit drag-session behavior that XCTest cannot exercise — verification was done against the `pane-drag` log on a running build (counts above).

## Smoke Test Checklist

| # | Scenario | Expected |
|---|----------|----------|
| 1 | Split a pane (⌘D), drag one by its handle, press Esc mid-drag | Drag ends; both panes still accept clicks and text selection |
| 2 | Immediately drag the same handle again | Blue drop-zone highlight appears as normal |
| 3 | Drag a pane, release outside the window | Same as #1 — no frozen overlay |
| 4 | Drag a pane and drop it back on itself | Same as #1 |
| 5 | After any of the above, drag a file from Finder into the terminal | Path is inserted |
| 6 | Drag a pane onto another pane's edge zone | Split happens as before (drop path unchanged) |
| 7 | With the file tree and editor both open, drag the divider between them | Width follows the mouse smoothly, no jitter |
| 8 | Drag that divider to both extremes | Clamps at 150 / 500 pt without snapping back |
| 9 | Drag a pane, then check the log | `[pane-drag]` shows `drag started` → … → `performDrop` or `drag cancelled` |
| 10 | Repeat #1 ten times | Every `drag started` is matched by a `performDrop` or a `drag cancelled` |
| 11 | Split a pane, double-click its three-dot handle | That pane fills the tab; sibling hidden; divider gone |
| 12 | Double-click the handle again | Split restores at the prior ratio |
| 13 | Double-click a non-focused pane's handle | That pane maximizes, not the focused one |
